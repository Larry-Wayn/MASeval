# MAQAS 毕设论文答辩与软件验收模拟问答

本文档根据毕业论文《正文.docx》和当前 MAQAS 项目代码整理，用于模拟毕业设计论文答辩与软件验收。回答内容尽量采用答辩现场可直接表述的口吻。

## 一、答辩总述准备

### Q1：请用 1 分钟概括你的毕业设计做了什么？

本课题面向大语言模型驱动的多智能体系统测试评估问题，核心目标不是单纯做一个问答程序，而是构建一套能够评价 LLM 多智能体系统的多维指标体系。论文将评价内容划分为个体智能水平、协作效率、系统稳定性和任务完成度四个维度，并在 CommonsenseQA 常识问答任务上实现了一个由 Analyst、Reasoner、Validator 组成的多智能体问答系统。实验部分通过单智能体基线、上下文等价基线、完整 MAS 和六组消融配置，分析不同角色和协作机制对准确率、输出规范性、稳定性和通信开销的影响。

### Q2：你的论文核心研究问题是什么？

核心问题是：如何系统化评价 LLM 多智能体系统，而不是只看最终准确率。现有很多评估方式关注某个任务上的成功率，但多智能体系统的关键还包括单体能力、协作是否真的带来增益、通信代价是否合理、输出是否稳定和可解析。我的工作就是把这些评估需求组织成四维框架，并通过代码实验验证这些指标能够揭示系统不同模块的作用。

### Q3：你的工作创新点在哪里？

主要有三点。第一，提出了“通用一级维度 + 场景化二级指标”的评价组织方式，使指标体系既能保持统一框架，又能适配问答、代码生成、规划决策、协商博弈等不同 LLM-MAS 场景。第二，在协作效率中引入上下文等价基线，把 Analyst 带来的信息增益和 Validator、Revision 等协作机制带来的净增益区分开。第三，除了准确率外，还加入答案提取率、答案确定性、选项扰动鲁棒性、重复运行稳定性和通信开销等指标，更完整地反映系统可用性。

### Q4：为什么选择 CommonsenseQA 作为实验任务？

CommonsenseQA 是多项选择常识推理任务，既有标准答案，便于计算准确率，又要求模型理解题干、比较多个候选选项、排除干扰项，适合观察推理过程和协作机制。相比开放式生成任务，它的结果更容易自动评测；相比简单分类任务，它又能体现推理、验证、答案格式等多智能体协作要素。

### Q5：为什么你的研究对象限定为 LLM-based agents，而不是传统 MAS？

传统 MAS 通常强调规则代理、仿真个体、强化学习智能体或分布式控制实体；而本课题关注的是以大语言模型作为推理、规划、通信核心的智能体。LLM agents 的通信主要通过自然语言完成，输出具有生成式随机性和格式不确定性，因此测试重点不仅包括任务结果，还要关注推理文本、答案可解析性、通信 token 成本和角色协作过程。这与传统 MAS 的评价需求有明显区别。

### Q6：你的四维评价框架分别解决什么问题？

个体智能水平回答“单个智能体本身强不强”；协作效率回答“多智能体协作是否比单体更有效，以及代价多大”；系统稳定性回答“系统面对输入扰动和随机采样时是否稳定”；任务完成度回答“完整系统最终是否准确、明确、规范地完成任务”。四个维度从基础能力、协作过程、鲁棒性和最终输出质量四个角度形成互补。

### Q7：为什么不能只用准确率评价多智能体系统？

准确率只能说明最终答案是否正确，不能说明系统为什么正确、是否通过高成本重复调用才正确、输出是否稳定、答案是否可解析、多个智能体是否真的产生了协作收益。例如本实验中完整 MAS 准确率相对单智能体提升 2.95 个百分点，但进一步分解发现其中 2.70 个百分点来自 Analyst 上下文，纯协作增益只有 0.25 个百分点。如果只看准确率，就会高估协作机制本身的贡献。

### Q8：论文中“上下文等价基线”的意义是什么？

上下文等价基线用于控制变量。完整 MAS 中 Reasoner 能看到 Analyst 的分析，如果直接把完整 MAS 和纯单智能体比较，提升可能只是因为多了一段分析上下文，而不是因为多智能体协作机制更好。因此我设置了 S2_Reasoner+Analyst，也就是把 Analyst 的输出直接提供给 Reasoner，但不启用 Validator 和 Revision。这样可以区分“信息增益”和“协作净收益”。

### Q9：你的协作增益是怎么计算的？

我使用三个准确率：单智能体准确率 single_acc、上下文等价基线准确率 context_acc、完整 MAS 准确率 multi_acc。原始协作增益是 multi_acc - single_acc，上下文增益是 context_acc - single_acc，纯协作增益是 multi_acc - context_acc。实验中 S1 为 81.98%，S2 为 84.68%，S6 为 84.93%，所以原始增益约 2.95 个百分点，上下文增益约 2.70 个百分点，纯协作增益约 0.25 个百分点。

### Q10：从实验结果看，哪个模块贡献最大？

从准确率角度看，Analyst 贡献最大。S1_SingleReasoner 的准确率为 81.98%，加入 Analyst 后 S2 提升到 84.68%，提升 2.70 个百分点。完整 MAS S6 为 84.93%，相对 S2 只提升 0.25 个百分点。因此主要性能提升来自 Analyst 提供的问题分析上下文。

### Q11：Validator 和 Revision 是否没有价值？

不能这么理解。Validator 和 Revision 对准确率提升有限，但它们显著提升了输出规范性和确定性。完整 MAS 的严格格式率达到 98.28%，提取失败率降到 0.98%，答案明确率达到 97.38%，不确定表达比例降到 0.90%。这说明 Validator 的主要价值不是单纯提高正确率，而是让系统输出更适合自动化评测和后续程序处理。

### Q12：为什么 S5_FullMAS_NoRevise 的准确率比 S6_FullMAS 略高？

实验中 S5 准确率为 85.09%，S6 为 84.93%，差距只有 0.16 个百分点，属于很小的边际差异。可能原因是 Revision 机制在少量样本中触发后，Validator 的反馈并不一定总能把 Reasoner 引向正确答案，反而可能引入过度修正。不过 S6 的严格格式率、提取失败率和答案明确率更好，说明修正机制更明显改善了输出质量，而不是准确率。

### Q13：S3 只加入 Validator 后准确率为什么下降？

S3 是 Reasoner+Validator，但没有 Analyst，也不允许修正。此时 Validator 只能做一次性后验判断，如果它误判或输出“需要修正”但系统不继续修正，就可能导致最终答案提取失败或沿用不理想结果，所以准确率从 S1 的 81.98% 降到 80.51%。但 S3 的严格格式率达到 89.68%，说明 Validator 对格式规范仍然有效。

### Q14：你的消融实验为什么设置六组？

六组配置对应 Analyst、Validator、Revision 三个核心模块的逐步组合。S1 是纯 Reasoner 基线；S2 测 Analyst 上下文；S3 测一次性 Validator；S4 测 Validator 加 Revision；S5 测完整三角色但不修正；S6 是完整系统。这样可以比较单模块贡献、模块组合贡献和完整系统表现。

### Q15：你的系统为什么采用 Analyst -> Reasoner -> Validator 的串行结构，而不是多个 Agent 投票？

因为本文的目标是测试“分析、推理、验证、修正”这一类常见 LLM-MAS 工作流。串行结构角色边界清晰，便于将中间状态记录到 AgentState 中，也便于进行消融分析。投票式结构适合研究独立多路径答案融合，但本课题更关注前置分析、后验验证和反馈修正对问答任务的影响。

### Q16：这种串行结构会不会导致智能体之间不独立？

会，所以论文和代码中都把一致性解释为 pipeline consistency，而不是完全独立一致性。Reasoner 依赖 Analyst 输出，Validator 又依赖 Reasoner 输出，因此三个智能体答案一致并不代表三个独立判断者达成共识。这个局限在答辩中需要主动说明，也是后续改进方向之一。

### Q17：Cohen’s Kappa 在这里的作用是什么？

Kappa 用于衡量超出随机一致性的智能体答案一致程度。普通一致率只看答案是否相同，但没有扣除偶然一致的可能性。Kappa 通过实际一致率和随机一致率的差异来衡量一致性强弱。不过当前实现仍基于流水线输出，因此它更适合作为辅助参考，而不是严格的独立协商一致性证明。

### Q18：推理可行性指标怎么避免“伪推理”？

代码中没有只看“因为”“所以”这类词是否出现，而是联合判断输出长度、答案是否合法、是否包含至少两个强因果推理词，以及推理词附近是否出现选项字母。只有答案有效时才有基础分，过程质量再占 0.6 权重。这样可以降低模板化空话被误判为高质量推理的风险。

### Q19：推理覆盖质量为什么要看选项文本而不只看 A/B/C/D/E？

因为模型输出中出现 A/B/C/D/E 并不等于真正分析了对应选项，题目复述或格式本身就可能包含选项字母。当前代码优先使用选项文本前若干字符作为关键词，统计推理文本是否覆盖选项内容，同时检查排除词是否和选项字母在上下文窗口中共现，并判断是否同时有肯定和否定评价词。

### Q20：位置偏差实验怎么保证公平？

选项顺序扰动时，代码会同步更新正确答案标签。也就是说，原本正确选项如果从 C 被打乱到 A，那么 ground truth 也会更新为 A。这样评估的是模型是否理解选项语义，而不是死记原始选项字母。

### Q21：重复运行稳定性为什么有必要？

大语言模型输出具有随机性，尤其本项目默认 temperature 为 0.7。同一道题多次运行可能出现不同答案。重复运行稳定性可以衡量系统输出是否一致，也能发现模型知识边界或推理不确定样本。论文中使用每题最高频答案比例表示稳定性，并结合 pass@1 和 Beta 置信区间描述正确率估计的不确定性。

### Q22：通信开销为什么重要？

多智能体系统通常比单智能体调用更多模型、产生更多中间文本。如果准确率只提升很小，但 token 成本和延迟显著增加，那么系统未必值得使用。本实验中 S1 平均输出字符数约 169，S6 约 357，说明完整 MAS 带来了更高通信开销。因此评价时需要同时看性能收益和成本。

### Q23：你的 total_tokens 字段是真正的 token 吗？

现在已经是。代码会从 DeepSeek/OpenAI 兼容接口返回的 `usage` 字段读取 `prompt_tokens`、`completion_tokens` 和 `total_tokens`，并在多智能体状态中累加。输出文本字符数单独保存在 `total_chars` 中，用于和旧实验的字符开销进行对比。需要注意的是，如果读取旧 checkpoint，缺少 API usage 字段，评估器才会退回到旧版字符数估算逻辑。

### Q24：实验结论能否证明多智能体系统一定优于单智能体？

不能泛化到所有任务。本文实验只能说明在 CommonsenseQA 常识问答任务和当前 DeepSeek 模型、提示词、工作流设置下，引入 Analyst 明显提升准确率，Validator 和 Revision 主要改善格式与确定性。多智能体是否优于单智能体依赖任务类型、角色设计、模型能力和成本约束，所以论文更强调评价框架和分析方法，而不是绝对结论。

### Q25：论文最大局限是什么？

主要局限有四点。第一，实验任务集中在 CommonsenseQA，虽然论文讨论了跨场景指标映射，但代码验证主要是问答场景。第二，当前一致性评估基于流水线输出，智能体并非完全独立。第三，当前已记录 API token usage，但端到端延迟、真实费用和更细粒度的请求级成本还可以继续补充。第四，指标中仍有一些启发式规则，例如答案抽取、推理词匹配和覆盖率计算，后续可以引入语义相似度或 LLM-as-Judge 提高鲁棒性。

### Q26：如果老师问“你的评价框架有什么通用性”，怎么回答？

通用性体现在一级维度稳定、二级指标可替换。个体能力、协作效率、系统稳定性、任务完成度适用于多数 LLM-MAS；但具体指标要按场景实例化。问答场景使用准确率、选项覆盖、答案提取率；代码生成场景可以替换为编译成功率、单元测试通过率、缺陷修复轮次；规划场景可以替换为计划可行率、约束满足率和扰动恢复率。因此框架提供的是组织方法，而不是要求所有场景使用完全相同公式。

### Q27：如果老师问“为什么不用 LLM-as-Judge”，怎么回答？

LLM-as-Judge 能提供语义层面评价，但也会引入裁判模型偏见、成本和复现性问题。本文选择 CommonsenseQA 作为主要实验场景，是为了优先保证指标可计算、可复现、可自动验证。因此准确率、格式率、提取率、扰动稳定性等都可以由程序直接计算。后续扩展到开放式任务时，可以将 LLM-as-Judge 作为补充指标，而不是完全替代可验证指标。

### Q28：如果老师质疑“关键词指标太简单”，怎么回应？

可以承认关键词指标是启发式近似，但说明已经做了防虚高设计。例如推理可行性要求答案合法、长度、强因果词和选项关联同时考虑；覆盖质量也不只是统计选项字母，而是结合选项文本、排除语境和双向比较。它的优点是可复现、低成本、便于批量评估；不足是语义理解有限，未来可以加入句向量相似度、NLI 判断或 LLM 裁判来增强语义评估。

### Q29：你的实验数据量是多少？结果是否可靠？

从结果文件看，消融实验使用了 CommonsenseQA dev 数据，准确率数值约对应 1221 条样本规模。稳定性实验中重复运行默认取前 10 题、每题 5 次，这部分样本较小，更适合作为稳定性方法演示，而不是高置信统计结论。因此答辩时可以强调：准确率和消融结果基于较完整样本，更有参考价值；重复稳定性部分后续应扩大样本和重复次数。

### Q30：论文结论一句话怎么总结？

本文证明了：对 LLM 多智能体系统的评估不能只看最终准确率，而应同时关注单体能力、协作增益来源、稳定性、输出规范性和成本。实验表明 Analyst 是准确率提升的主要来源，Validator 和 Revision 更主要改善答案格式、可解析性和确定性。

## 二、软件验收模拟问答

### Q31：请介绍一下项目代码整体结构。

项目主要由实验入口、工作流、评估器、并发执行器和结果绘图几部分组成。`main.py` 调用 `experiments.py` 执行完整四维评估；`workflow.py` 实现 Analyst、Reasoner、Validator 三智能体 LangGraph 流程；`evaluator.py` 计算 I1 到 I4 指标；`ablation.py` 和 `run_ablation.py` 实现六组消融实验；`concurrent_runner.py` 负责并发、重试和断点续跑；`plot_results.py` 读取结果并生成图像。

### Q32：系统运行前需要配置什么？

需要 Python 环境、依赖包和 DeepSeek API 配置。项目通过 `config.py` 读取环境变量，关键变量包括 `DEEPSEEK_API_KEY`、`DEEPSEEK_MODEL`、`DEEPSEEK_TEMPERATURE`、`DEEPSEEK_BASE_URL`、`MAS_MAX_WORKERS`、`MAS_MAX_RETRIES` 等。其中 `DEEPSEEK_API_KEY` 是必填项，未设置会直接抛出错误。

### Q33：完整实验怎么运行？

可以运行 `python main.py` 使用默认数据集，也可以运行 `python main.py --n 200` 指定样本数，或使用 `python main.py --data data/dev_rand_split.jsonl --n 1221` 跑完整 dev 集。`--workers` 控制并发线程数，`--no-resume` 可以忽略已有断点强制重跑，`--num-perms`、`--stability-k`、`--stability-n` 分别控制稳定性实验参数。

### Q34：消融实验怎么运行？

消融实验入口是 `run_ablation.py`。常用命令是 `python run_ablation.py` 或 `python run_ablation.py --n 50`。它会依次运行 S1 到 S6 六组配置，并输出 `results/ablation_summary.csv`、`results/ablation_summary.json` 和 `results/ablation_per_sample.json`。

### Q35：软件的核心业务流程是什么？

核心流程是：加载 CommonsenseQA 数据，构造问题和选项；运行单智能体基线和多智能体系统；多智能体系统中先由 Analyst 分析题目，再由 Reasoner 生成推理和答案，最后由 Validator 检查推理并输出最终答案；如果 Validator 认为需要修正且未超过上限，则回到 Reasoner 重新推理。运行结果交给 evaluator 计算四维指标，并写入结果文件。

### Q36：LangGraph 在系统中起什么作用？

LangGraph 用来把三个智能体节点组织成状态图。`AgentState` 保存问题、选项、各智能体输出、消息记录、最终答案、轮次和修正标记。图结构中固定边是 analyst -> reasoner -> validator，validator 后通过条件边判断是否回到 reasoner 或结束。这样可以让多智能体协作流程结构化、可追踪、可复现。

### Q37：AgentState 中最关键的字段有哪些？

关键字段包括 `question`、`choices`、`messages`、`analyst_output`、`reasoner_output`、`validator_output`、`final_answer`、`round_count`、`needs_revision` 和 `revision_count`。其中 `messages` 记录协作过程，`final_answer` 是最终答案，`needs_revision` 和 `revision_count` 控制修正循环。

### Q38：系统如何判断是否需要修正？

Validator 输出后，代码用正则匹配“需要修正”“请重新推理”“推理有误请修正”等表达。如果匹配到，就设置 `needs_revision=True`，并增加 `revision_count`。条件边会根据这个状态决定是否回到 Reasoner。

### Q39：修正循环如何避免无限循环？

有两层限制。第一，`SYSTEM_CONFIG["max_rounds"]` 限制最大验证轮数，默认是 5。第二，当前 `workflow.py` 中额外限制 `revision_count < 2`，也就是最多触发两次修正。消融版 `ablation.py` 中则通过 `MASConfig.max_revisions` 控制。

### Q40：答案是怎么从模型输出中提取的？

`utils.extract_answer()` 按优先级提取答案。最高优先级是 `最终答案:X`，其次是 `答案:X`，然后是“选 A”“答案是 A”“应该是 A”等语境表达，再然后是括号中的选项字母，最后才在文本末尾 50 个字符中做兜底匹配。如果都失败，返回 `UNKNOWN`。

### Q41：为什么要区分 strict_rate、standard_rate、fallback_rate 和 unknown_rate？

因为“能抽出答案”不代表输出质量一样。`strict_rate` 表示严格使用 `最终答案:X`，最适合自动评测；`standard_rate` 是 `答案:X`；`fallback_rate` 表示依赖宽松规则提取，可靠性较弱；`unknown_rate` 表示提取失败。这样比单一提取成功率更有区分度。

### Q42：并发和断点续跑是怎么实现的？

`concurrent_runner.py` 使用 `ThreadPoolExecutor` 并发执行 LLM 调用，适合这种 IO-bound 任务。每条任务完成后会追加写入 JSONL checkpoint，记录 `__idx` 和结果。下次运行时会读取 checkpoint，跳过已经完成的样本，从而支持长时间实验中断后续跑。

### Q43：失败重试机制是怎样的？

`llm_client.py` 对超时、连接错误、429 限流和 5xx 服务端错误抛出异常，`concurrent_runner.py` 捕获后按指数退避重试。默认最多重试 3 次，等待时间是 `retry_base_delay * 2^(attempt - 1)`。如果最终仍失败，会返回 `_error` 占位，实验主流程再转换成 `UNKNOWN`，避免程序崩溃。

### Q44：为什么 429 限流要特殊处理？

429 表示 API 限流，服务端可能返回 `Retry-After`。`llm_client.py` 会先按该字段等待一段时间，再抛出 `LLMRateLimitError` 交给上层重试。这样比立即重试更稳定，也能减少持续触发限流的风险。

### Q45：系统结果文件有哪些？

完整四维实验会输出 `results/full_evaluation_report.txt`、`results/full_evaluation_summary.json` 和多个 checkpoint。消融实验会输出 `results/ablation_summary.csv`、`results/ablation_summary.json`、`results/ablation_per_sample.json`。绘图脚本会在 `results/figures/` 下生成图像和 `plot_data.json`。

### Q46：绘图脚本的作用是什么？

`plot_results.py` 读取消融实验汇总和 checkpoint，重新计算或整理部分指标，然后生成准确率对比、协作增益分解、通信开销、格式提取质量和答案确定性等图像。它不参与模型推理，只负责结果可视化。

### Q47：验收时如果要求现场演示，你会怎么演示？

我会先展示项目目录结构和 `PROJECT_EXPLANATION.md`，说明各模块职责；然后展示 `.env` 配置项；接着运行一个小样本命令，例如 `python run_ablation.py --n 5` 或 `python main.py --n 5`，避免现场等待太久；运行后打开 `results/ablation_summary.json` 或 `results/full_evaluation_report.txt` 查看结果；最后展示 `plot_results.py` 生成的图像和论文中的结论如何对应。

### Q48：如果现场没有 API Key，软件还能验收吗？

完整推理必须依赖 DeepSeek API Key；没有 API Key 无法现场调用模型。但可以展示已有 `results/` 结果文件、代码结构、断点 checkpoint 和绘图输出。如果必须离线演示，后续可以增加 mock LLM 或读取缓存结果的模式，用固定响应模拟模型调用。

### Q49：你的代码如何保证实验可复现？

一方面，数据集路径、样本数、排列次数、重复运行次数、并发数等都通过命令行参数或环境变量配置；另一方面，选项打乱使用 seed 控制，checkpoint 保存每条样本结果，结果汇总保存为 JSON/CSV 文件。需要注意的是，LLM 调用本身存在随机性，temperature 为 0.7 时完全逐字复现不现实，但指标流程和已有结果是可追踪的。

### Q50：系统的安全性或隐私风险是什么？

主要风险是 API Key 泄露和数据外发。代码通过环境变量读取 API Key，不应把 `.env` 提交到仓库；调用模型 API 时题目文本会发送到外部服务，因此如果换成敏感业务数据，需要做脱敏或使用私有化模型。当前 CommonsenseQA 是公开数据集，隐私风险较低。

### Q51：如果模型输出格式不遵守要求，系统怎么办？

首先 Validator 的提示词明确要求最后一行使用 `最终答案:X`。如果仍不规范，`extract_answer()` 会按多级规则兜底提取。如果 Validator 没写清答案但也没有要求修正，代码会退回到 Reasoner 的答案。最终仍失败则返回 `UNKNOWN`，并体现在 `unknown_rate` 中。

### Q52：当前代码有哪些可以改进的地方？

第一，可以继续记录端到端延迟、请求级费用和更细粒度的 token 成本。第二，可以把 `revision_count < 2` 改为完全配置化，避免硬编码。第三，可以增加 mock LLM 和单元测试，方便离线验收。第四，可以改进 `extract_answer()` 的兜底反向搜索逻辑和复杂输出解析。第五，可以将一致性评估扩展为独立多 Agent 轮询，而不只基于流水线输出。

### Q53：为什么使用 ThreadPoolExecutor，而不是多进程或异步？

LLM API 调用主要瓶颈是网络 IO，不是 CPU 计算，因此线程池足够。多进程会带来更高的进程管理开销，异步实现虽然也适合 IO，但需要重写请求和错误处理逻辑。当前线程池实现简单、稳定，并且结合 checkpoint 可以满足实验需求。

### Q54：如果某条样本失败，会不会影响整个实验？

不会。`run_in_parallel()` 对单条任务独立重试，最终失败后只把该样本记录为 `_error`。实验主流程会把失败样本转换成 `UNKNOWN` 占位，并继续计算整体指标。这样可以避免长时间实验因为个别 API 错误全部中断。

### Q55：如何验证消融实验确实关闭了某个模块？

`ablation.py` 中关闭 Analyst 时使用 `_noop_analyst()`，它不调用 LLM，只写入空分析和 `[disabled]` 消息；关闭 Validator 时使用 `_noop_validator()`，它直接从 Reasoner 输出中抽取答案，不做验证和修正。返回结果中也保存了配置开关，可以通过 `ablation_summary.json` 查看每组 `enable_analyst`、`enable_validator`、`enable_revision` 的值。

### Q56：软件验收时如何说明“这个项目不仅是脚本堆砌”？

可以从工程结构说明。系统有清晰的分层：`workflow.py` 负责业务工作流，`evaluator.py` 负责指标计算，`concurrent_runner.py` 负责执行可靠性，`llm_client.py` 负责外部 API，`ablation.py` 负责可配置结构，`plot_results.py` 负责结果展示。实验入口和评估逻辑分离，结果可持久化，失败可重试，长任务可断点续跑，这些都体现了完整实验系统的工程化设计。

### Q57：如果老师要求解释一个样本从输入到输出的过程，你怎么说？

一条样本首先由 `data_loader.py` 从 JSONL 中解析出 question、choices 和 answer。进入多智能体流程后，Analyst 读取题目和选项，输出问题分析；Reasoner 读取原始题目、选项和 Analyst 分析，生成推理过程和答案；Validator 读取 Reasoner 输出，判断是否合理。如果合理，输出 `最终答案:X`；如果不合理，输出修正意见并触发 Reasoner 重推理。最后系统返回 conversation、answer、metrics 和 final_state，评估器再将 answer 与标准答案比较。

### Q58：项目是否支持不同模型？

支持兼容 OpenAI Chat Completions 格式的模型服务。`llm_client.py` 中 base_url、model、api_key 都来自环境变量。默认是 DeepSeek，但只要目标服务兼容 `/chat/completions` 接口，就可以通过 `DEEPSEEK_BASE_URL` 和 `DEEPSEEK_MODEL` 替换。

### Q59：如果验收老师问“你怎么证明结果不是偶然”，怎么回答？

可以说明实验采用了完整 dev 数据上的消融对比，且设置了多个结构配置，不只比较单次运行。关键结论不是来自单一数字，而是来自多组结果的一致趋势：Analyst 提升准确率，Validator 提升严格格式率和明确率，Revision 对准确率边际贡献小但改善解析质量。对于随机性，论文也设计了重复运行稳定性实验；不足是重复样本数仍可扩大。

### Q60：如果要继续完善这个系统，优先做什么？

优先做三件事。第一，完善评估严谨性，补充延迟、费用和更多重复运行样本。第二，增强跨场景验证，把框架迁移到代码生成或规划任务。第三，提高工程可验收性，加入 mock 模式、单元测试和配置化修正上限，使系统在无 API 或低成本条件下也能完整演示。

## 三、答辩追问快速记忆版

### 1. 最核心结论

完整 MAS 准确率为 84.93%，相对单智能体 81.98% 提升 2.95 个百分点；其中 Analyst 带来的上下文增益约 2.70 个百分点，纯协作增益约 0.25 个百分点。Validator 和 Revision 对准确率提升有限，但显著提高严格格式率、答案可解析性和答案确定性。

### 2. 最可能被问到的风险点

当前一致性评估是流水线一致性，不是完全独立 Agent 共识。新结果中的 `total_tokens` 来自 API usage，但旧 checkpoint 仍可能是字符估算口径。推理质量和覆盖质量部分指标使用启发式规则。实验主要验证问答场景，跨场景通用性还需要更多任务支撑。

### 3. 最推荐主动强调的话

本课题的重点不是证明“多智能体一定更准”，而是提出一种能够拆解多智能体系统表现的测试评价方法。通过上下文等价基线和消融实验，可以看出系统性能提升来自哪里、代价是什么、哪些模块改善的是准确率、哪些模块改善的是输出规范性。
